termCtl op 1001 ignores SIGTSTP (18), while its doc says SIGCONT

Seen in oukmiz (consult round 20261109-170231-3f70, sol): `Posix/Term.lean`'s op 1001 calls `signal(18, SIG_IGN)`, and the doc comment of `termCtl` says it "ignores SIGCONT". On macOS (`<sys/signal.h>`: SIGTSTP 18, SIGCONT 19) signal 18 is SIGTSTP. oukmiz only noted the mismatch in `termOpsRaw`'s private comment. Decide which is intended: keep ignoring SIGTSTP (a raw-mode program has no Ctrl-Z anyway, but a `kill -TSTP` would otherwise stop it with the screen in raw mode) and correct the public doc, or change the code to what the doc says. Either changes the documented contract consumers (rr, rr2, lean-tui) read.

Options: correct the doc to SIGTSTP | ignore SIGCONT (19) as documented | ignore both

Decided with the models on 2026-11-09 as the owner asked (consult round 20261109-172543-af7f, sol and argon agreed): option (a). Ignoring SIGCONT would do nothing (it always continues the process), and catching SIGTSTP to suspend and resume is a separate protocol (persistent handlers, re-entering the alternate screen clears it and only the program can redraw), not this item. Checked by the session: `signal(18, SIG_IGN)` came verbatim from rr's first viewer commit (2026-11-02) with no stated reason; an ignored disposition survives exec, and `defaultSignals` (`Posix/Process.lean`) resets only 1, 2, 3, 13 and 15, so children started after op 1001 (rr2-view's `git`, rr's `rr run --kill`) inherit SIGTSTP ignored. Work: correct `termCtl`'s doc to "ignores SIGTSTP (so `kill -TSTP` cannot stop it with the terminal raw)" and drop the private note about the mismatch; leave SIGCONT alone; add 18 to `defaultSignals` and its doc. Test, synchronized through pipes, no sleeps: in a child after `termCtl 1001`, SIGTSTP is ignored and SIGCONT keeps its default; after `defaultSignals`, SIGTSTP is back to its default. Consumers follow up in their own queues (lean-tui's `guardSignals` doc copies "ignores SIGCONT"; children rr and rr2 start through Lean's `IO.Process` do not call `defaultSignals`): name them in the report.
